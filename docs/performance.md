# Производительность

Производительность — приоритет №1. Просадка FPS или времени кадра выше порога — баг и блокер релиза.

## Цели

| Метрика | Цель |
|---|---|
| FPS | стабильные 60 в тяжёлых играх; 90/120/144+, где игра позволяет |
| 1% low | ≥ 85% от среднего FPS |
| Статтеры | нет статтеров при повторном появлении шейдеров |
| Задержка ввода | < 30 мс при ≥ 90 FPS или VRR; < 45 мс при 60 Гц с VSync |
| Старт из снапшота | < 5 с |

Определения метрик совпадают с [`rustdroid-telemetry::FrameStats`](../crates/telemetry/src/frame_stats.rs):
средний FPS = кадры / суммарное время; 1% low = FPS при 99-м перцентиле времени кадра.

## Железо

Тестовая конфигурация не фиксируется: RustDroid подстраивается под машину сам.
- Число vCPU по умолчанию считается от числа P-ядер (на гибридных Intel E-ядра для vCPU не используются).
- Адаптер по умолчанию — самый производительный (`DXGI_GPU_PREFERENCE_HIGH_PERFORMANCE`), на
  ноутбуках экспортируются `NvOptimusEnablement` и `AmdPowerXpressRequestHighPerformance`.
- RAM инстанса по умолчанию зависит от RAM хоста.
- Частота дисплея гостя по умолчанию равна частоте монитора (60–144+ Гц).

Каждый бенч-прогон сохраняет конфигурацию машины (CPU, GPU, драйвер, RAM, монитор, сборка Windows)
рядом с результатами, поэтому сравнение идёт только между прогонами на одной машине.

## Узкие места и решения

| Узкое место | Решение |
|---|---|
| Выход vCPU в user mode | doorbells для notify, EVENT_IDX, MSI-X напрямую, LAPIC в гипервизоре, никакого PIO в горячем пути |
| Декодер gfxstream (CPU хоста) | отдельные потоки на P-ядрах; vCPU ≤ P-ядер − 2 |
| Копии кадра | общий NT handle Vulkan→D3D12, `VK_EXT_external_memory_host` для blob |
| Два независимых VSync | VSync гостя от хоста (метки VBlank) |
| Компиляция шейдеров | постоянные кэши: драйвер, `VkPipelineCache`, ANGLE, Android |
| Задержка вывода | waitable swapchain, `SetMaximumFrameLatency(1)`, tearing для VRR |
| Таймеры | high-resolution waitable timer для лимитера |
| SLAT-фолты при первом касании | prefault всей RAM, опционально страницы 2 МБ |
| Планировщик Windows | CPU Sets, MMCSS, отключение power throttling для наших потоков |
| UI | отдельный поток, вершины egui — двойным буфером, рисуются тем же проходом |
| ARM-трансляция | x86_64-сборки игр, когда они есть; кэш трансляции |

## Сборка

- `release`: `opt-level = 3`, `lto = "fat"`, `codegen-units = 1`, `.pdb` отдельно.
- Базовая цель `x86-64-v2`; горячие участки — рантайм-диспетчеризация под AVX2 (`is_x86_feature_detected!`).
- PGO: планируется после этапа 4, когда появятся представительные сценарии (`cargo pgo` на бенч-снапшотах).

## Измерение

### Оверлей (этап 3)

FPS, 1% low, график времени кадра, загрузка vCPU и GPU, задержка ввода. Оверлей рисуется в том
же проходе, что и кадр гостя.

### Tracy

```powershell
cargo build --profile profiling --features tracy   # фича появится на этапе 1
```

### PresentMon

```powershell
PresentMon.exe --process_name rustdroid.exe --output_file presentmon-run.csv --timed 60
```

CSV прикладывается к issue «Проблема производительности».

### Задержка ввода (этап 3+)

Тестовый APK в госте меняет цвет экрана по касанию. Хост ставит метку времени на событии ввода
и ловит момент Present кадра с новым цветом. Получается сквозная задержка без внешней камеры.

## Бенчмарки и порог регрессии

1. **Микробенчмарки** (criterion) для горячих путей: `cargo bench --workspace --bench '*'`.
2. **Сценарии** (этап 3+): снапшот игры + скрипт ввода, прогон N секунд, метрики из PresentMon.

Сравнение с базовой линией:

```powershell
cargo bench --workspace --bench '*' -- --save-baseline base   # на main
cargo bench --workspace --bench '*' -- --baseline base         # на ветке
cargo xtask bench-check --threshold 5
```

### Self-hosted раннер

Бенчмарки запускаются на ноутбуке мейнтейнера по запросу: вручную (`workflow_dispatch`) или
меткой `run-bench` на PR из этого репозитория. PR из форков на раннере не запускаются.

Регистрация раннера (один раз):

1. Settings → Actions → Runners → New self-hosted runner → Windows x64; выполните показанные команды.
2. Добавьте метки: `windows`, `x64`, `gpu`.
3. Запускайте `run.cmd` только на время прогона (без установки как службы).
4. Перед прогоном: питание от сети, режим «Макс. производительность», закрыты тяжёлые приложения.
